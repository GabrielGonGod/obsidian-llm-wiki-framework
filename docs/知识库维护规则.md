# LLM 知识库维护规则

本资料库采用 Karpathy `LLM Wiki` 思路：LLM 不只是检索文件，而是持续维护一个会增长、会交叉引用、会更新旧结论的 Markdown 知识库。

核心原则：你负责记录、判断、取舍和创作；LLM 负责整理、归并、交叉引用、查漏补缺、维护索引和日志。

## 总体结构

- `LLM知识库系统/raw/`：原文层和证据层。重要原始资料、网页导出、PDF 摘录、数据、外部文档、有道原文镜像都放这里，默认只读。
- `知识管理/`：长期可复用知识，包括说明书、历史操作笔记、学习资料、教程、配置记录、经验复盘。这里是人和 AI 都要经常查的“知识工作区”。
- `备忘录/`：杂卡、快查备忘、信息备份、临散重要记录。这里不强求知识化；私人资料可以索引和调用，但默认不把明文秘密扩散到 wiki、稿件或公开内容。
- `爸爸的有道历史/`：家庭记忆档案。保留爸爸留下的有道云笔记、录音、附件和项目痕迹。这里不按普通知识库处理，不自动改写、合并、删减或评价。
- `灵感库/`：你的日常灵感入口。可以很碎、很口语、很临时，优先保证快速记录。
- `光的房间稿件/`：稿件、选题、脚本、口播、长文、发布版本。这里是创作生产区。
- `LLM知识库系统/raw/`：原始资料和有道原文镜像，尽量不修改正文。
- `LLM知识库系统/inbox/`：待处理资料和待整理片段。
- `LLM知识库系统/wiki/`：LLM 维护的结构化页面，包括主题页、人物页、项目页、概念页、对比页、综述页。
- `LLM知识库系统/queries/`：值得长期保存的问题、分析、表格、决策记录。
- `LLM知识库系统/index.md`：知识库总索引。新增或更新 wiki 页面后必须更新。
- `LLM知识库系统/log.md`：时间线日志。格式为 `## [YYYY-MM-DD] action | title`。

不要为了“整齐”把已有的 `知识管理/`、`灵感库/`、`光的房间稿件/`、`备忘录/` 全部搬进 `wiki/`。这些目录本身就是资料库的一部分；`wiki/` 是 LLM 编译出来的结构化层。

## LLM 系统目录的分工

`LLM知识库系统/inbox`、`raw`、`wiki`、`queries` 不是普通资料分类目录，而是 AI 处理资料时的流水线。

- `inbox/`：单层平盆收件箱，**故意不分子目录**。所有暂时不知道该放哪里的混杂资料、新剪藏、新导入、新摘录，都无脑丢进 inbox 根目录。分类是 AI 的工作，不是录入者的工作：AI 定期读取 inbox，判断类型、去重、拆分，再分发到最终工作区（`知识管理/`、`备忘录/`、`灵感库/`、`光的房间稿件/`、`raw/`、`wiki/`、`queries/`）。录入者若已明确类别，应直接放最终工作区，不必经过 inbox。详见 [[LLM知识库系统/inbox/_说明]]。
  - 历史变更：inbox 原本有 `00.待分拣 / 10.灵感片段 / 20.资料剪藏 / 30.说明书 / 40.历史稿件` 五个子目录，已于 2026-06-03 取消（理由见 log）。不要再创建这些子目录。
- `raw/`：原始证据层。重要原始资料、长文、网页导出、PDF 摘录、数据、外部文档可以在这里留一份不可改正文的备份。
- `raw/有道云笔记原文镜像/`：有道云迁移原文层，用于像有道云笔记一样查看和搜索原文；只做路径兼容和索引，不做知识提炼。
- `wiki/`：编译层。这里不存所有细节，只存 AI 从多个来源整理出的主题页、总览、概念页、对比页、决策页。
- `queries/`：问题和分析层。一次值得保留的提问、比较、决策分析、资料体检报告，放这里，方便以后复用。

处理完成后，资料通常会离开 `inbox` 的“待处理”状态，进入更合适的最终工作区：

- 可复用知识进入 `知识管理/`。
- 临散杂卡和快查备忘进入 `备忘录/`。
- 灵感和选题进入 `灵感库/`。
- 稿件和脚本进入 `光的房间稿件/`。
- 历史原文和迁移原貌优先放在 Obsidian 外部归档；仓库内只保留整理后的可用资料、纪念区副本和必要索引。
- 家庭记忆档案进入 `爸爸的有道历史/`，以保全、索引和温和导航为主。
- 跨资料的结构化结论进入 `LLM知识库系统/wiki/`。
- 一次性但有长期价值的分析进入 `LLM知识库系统/queries/`。

迁移资料完成整理后的收尾规则：

- 有道云迁移原始包已移出 Obsidian，外部位置：`<外部归档路径，按需替换>`。
- 后续整理时，优先使用仓库内已经落位的 `知识管理/`、`备忘录/`、`灵感库/`、`光的房间稿件/`、`爸爸的有道历史/` 和 `LLM知识库系统/wiki/`。
- 只有在需要校对原始迁移状态、补查遗漏附件、核对导出失败记录时，才回到外部归档。
- 外部归档的永久删除属于高风险动作，必须等待用户再次明确授权。

## 所有权

- 用户原文优先：`灵感库/` 和 `光的房间稿件/` 里的个人表达、口吻、草稿，不要未经要求重写成“标准 AI 文”。
- 家庭记忆优先：`爸爸的有道历史/` 里的内容不是普通资料资产，不要为了效率改写、合并、删除、评价或拆散。可以做索引、附件保全、时间线和温和主题导航。
- 知识可执行优先：`知识管理/` 里的说明书、操作笔记、学习资料，要整理成之后能复用、能搜索、能让 AI 接手执行的结构。
- LLM 维护层：`LLM知识库系统/wiki/`、`queries/`、`index.md`、`log.md` 由 LLM 主动维护。
- 来源层不可篡改：迁移来的旧笔记、原始文章、截图、PDF、录音等只做引用和摘取，不直接改写源文件。
- raw 原文镜像优先只读：如需整理、拆分、提炼，到 `知识管理/`、`灵感库/`、`光的房间稿件/` 或 `wiki/` 建新页面。
- 成稿需可追溯：每篇稿件尽量链接到相关灵感、资料、主题页和最终发布记录。

## 页面类型

### 灵感卡

用于突然想到的句子、选题、观察、素材联想。允许不完整。

建议字段：

- `type: idea`
- `status: seed | incubating | used | archived`
- `area: self-media | script | home | personal | research`
- `来源:` 灵感来源，可以为空
- `related:` 相关页面

### 素材卡

用于看到的案例、句子、视频、文章、评论、产品、人物、场景。

要求：

- 保留来源链接或截图位置。
- 区分“事实”“我的判断”“可用于哪个稿件”。
- 如果来源不可靠，标注 `待核对`。

### 主题页

用于长期积累的知识主题，例如家装、咖啡、内容表达、光的房间、视频选题方法。

要求：

- 开头说明这个页面回答什么问题。
- 列出主要来源。
- 保留“当前结论”“证据”“反例/冲突”“待追问”。
- 重要概念使用 Obsidian 双链。

### 知识卡

用于说明书、教程、操作笔记、学习资料、配置记录、踩坑记录。

建议字段：

- `type: knowledge`
- `domain: manual | howto | learning | config | troubleshooting | reference`
- `status: raw | distilled | verified | outdated`
- `owner_ai: codex | claude | chatgpt | any`
- `last_verified:` 最近验证日期

要求：

- 开头写“什么时候用这篇”。
- 操作类笔记必须有步骤、前置条件、风险、回滚方式。
- 学习类笔记必须有核心概念、例子、反例、下一步问题。
- 配置/账号/密钥类信息只放必要描述，不把敏感信息明文扩散到 wiki。

### 稿件项目

用于一篇具体稿件或视频。

建议阶段：

- `idea`：只有选题。
- `outline`：有结构。
- `draft`：有初稿。
- `editing`：正在改。
- `ready`：可发布。
- `published`：已发布。
- `archived`：弃用或搁置。

每个稿件项目至少包含：

- 选题一句话。
- 受众和场景。
- 核心观点。
- 素材来源。
- 大纲或脚本。
- 修改记录。
- 发布记录。

### 历史稿件

用于过去已经写过、发过或搁置的稿子。历史稿件优先作为参考资料、风格样本、主题资产和发布记录，不自动重写成新稿。

建议字段：

- `type: historical-draft`
- `status: raw | indexed | excerpted | revived | archived`
- `platform:` 公众号、抖音、小红书、视频脚本、朋友圈、内部稿等
- `year:` 年份或大致时间
- `topic:` 主题
- `published:` 是否发布

要求：

- 原稿正文不直接改写。
- 先建立标题、平台、年份、主题、状态、可复用价值和关联页面。
- 从旧稿摘出的好句、案例、标题要回链原稿。
- 如果旧稿要发展成新稿，创建新的稿件项目，不覆盖旧稿。

## 工作流

### capture：快速记录灵感

1. 先保存到 `灵感库/`，不要因为分类犹豫而中断记录。
2. 标题可以粗糙，但正文第一段要保留原始想法。
3. 只做轻量标签，不做过度整理。
4. 如果灵感明显可写稿，链接到 `光的房间稿件/稿件索引` 或创建稿件项目。

### incubate：把灵感养成选题

1. 定期读取 `灵感库/` 中 `status: seed` 或未整理页面。
2. 合并重复灵感，保留原始链接。
3. 抽出可写方向，更新到 `LLM知识库系统/wiki/写作与灵感系统`。
4. 对成熟灵感创建或更新稿件项目。
5. 修改灵感卡状态为 `incubating` 或 `used`。

### ingest：资料入库

1. 读取 `LLM知识库系统/index.md` 判断已有结构。
2. 优先读取 `LLM知识库系统/inbox/` 中的新混杂资料；如果整理旧迁移资料，则读取 `LLM知识库系统/raw/有道云笔记原文镜像/` 或指定来源。
3. 判断每份资料应该进入哪里：`raw/`、`知识管理/`、`灵感库/`、`光的房间稿件/`、`wiki/` 或 `queries/`。
4. 对需要保留原貌的资料，放入或保留在 `raw/`，不改正文。
5. 对长期可复用知识，写入或更新 `知识管理/`。
6. 对跨文档结论，写入或更新 `wiki/` 下的主题页、人物页、概念页。
7. 对值得保留的问题、比较和决策分析，写入 `queries/`。
8. 补充双链、来源、待办和冲突提示。
9. 更新 `index.md`。
10. 在 `log.md` 添加一条记录。

### capture-social：抖音/小红书收藏入库

把抖音、小红书收藏夹里的视频/图文转成素材卡。两段式：登录态在用户 Mac 浏览器，沙盒只负责转写。

**排除作者（重要）**：处理收藏时，跳过以下作者的视频，不入库、不转卡：
- `光的房间`（用户本人作品）
- `做家具的兵哥哥`
（识别作者时注意：抖音视频页主作者信息常和"推荐视频"侧栏作者混在一起，需定位主视频区域的作者，不能直接取页面里第一个"粉丝…获赞…"。）

抖音收藏的真实结构与已抓数据见 [[LLM知识库系统/raw/抖音收藏/抖音收藏总览]] 与 `raw/抖音收藏/抖音收藏目录_618条.md`。

1. 用 Claude in Chrome 打开收藏页（路径：左侧「我的」→收藏→视频）。**不要用 `video/{id}` 网址打开单条**（抖音会重定向到推荐流，打开的不是收藏）。
   - 文案层：在网格页 `get_page_text` 一次性取当前已加载每条收藏的完整文案。
   - 内容总结：**点击网格里的卡片**打开模态框 → 右侧点「问AI」自动生成「视频总结」(结构化分点)，这是素材卡最佳来源；作者在视频下方 `@用户名`；五角星点亮=已收藏。
2. 对每条调用 `LLM知识库系统/tools/transcribe_social.py`：
   - 自动路线：`python3 transcribe_social.py --url "<链接>" --note "为什么收藏"`（yt-dlp 下载 → ffmpeg 抽音轨 → faster-whisper 转中文字幕）。
   - 兜底路线：抖音签名下载失败或内容需登录时，请用户保存视频到本地，改用 `--file "<视频路径>"`。
3. 脚本产出「素材卡」写入 `inbox/`（frontmatter 含平台、链接、作者、收藏日期、已转写）。
4. 按 ingest 流程分发：自媒体选题素材通常进 `光的房间稿件/素材/` 或 `灵感库/`。
5. 仅处理用户本人收藏、用于个人创作参考；保留来源链接和作者以便追溯。转写文本可能有错别字，关键信息以页面原文为准。
6. 在 `log.md` 追加 `## [日期] capture-social | 平台 N 条`。

依赖：沙盒首次需 `pip3 install --break-system-packages yt-dlp faster-whisper`（ffmpeg 自带）。对应 skill：`.claude/skills/social-collect`。

### organize-knowledge：整理知识管理

1. 从 `知识管理/`、`说明书/`、根目录散落笔记或迁移旧笔记中选择一批资料。
2. 判断类型：说明书、操作笔记、学习资料、配置记录、问题复盘、参考资料。
3. 保留原文或原链接，必要时建立摘要版。
4. 输出可执行结构：用途、适用场景、步骤、注意事项、相关页面、待验证。
5. 对高频知识建立 `wiki/` 主题页；对低频资料保留在 `知识管理/` 并更新索引。
6. 更新 `知识管理/知识管理索引`、`LLM知识库系统/index.md` 和 `log.md`。

### query：提问和分析

1. 先读 `LLM知识库系统/index.md`。
2. 搜索相关 wiki、灵感、稿件和归档资料。
3. 回答时说明依据来自哪些页面。
4. 如果答案值得保存，写入 `queries/` 或更新相关 `wiki/` 页面。

### draft：写稿

1. 先找相关灵感、素材、主题页和旧稿。
2. 明确稿件类型：口播、长文、小红书、抖音脚本、公众号、提纲、标题库。
3. 保留你的原始表达，不要自动抹平风格。
4. 输出版本时标注 `v1/v2/发布版`。
5. 成稿后回链到用过的灵感和素材，把灵感状态改为 `used`。

### archive-drafts：纳入历史稿件

1. 旧稿先放入 `光的房间稿件/历史稿件/待整理/`。
2. 不改原文，先生成或补齐历史稿件索引卡。
3. 判断平台、年份、主题、发布状态和可复用价值。
4. 更新 [[光的房间稿件/历史稿件/_索引|历史稿件索引]]。
5. 把可复用的观点、案例、标题、结构或语气样本摘到 `光的房间稿件/素材/`，并回链原稿。
6. 如果旧稿可以变成新选题，创建或更新 `光的房间稿件/选题池/` 下的稿件项目。
7. 已发布稿补充到 `光的房间稿件/历史稿件/发布记录/`。

### lint：健康检查

定期检查：

- 断链、孤立页面、重复页面。
- 没有来源的结论。
- 旧结论被新资料推翻但未更新。
- 灵感库里长期没有处理的高价值片段。
- 稿件项目停在 `draft/editing` 太久。
- 应该沉淀成主题页却只散落在稿件里的概念。
- 知识管理里过期的操作步骤、失效链接、缺少验证日期的教程。

检查完成后更新 `log.md`，必要时生成 `queries/知识库体检 YYYY-MM-DD.md`。

## 质量规则

- 不把聊天中的临时回答当作事实；只有写入 wiki 并注明来源后，才算进入知识库。
- 遇到重复、冲突、过期信息时，不要悄悄覆盖，要标注“冲突”“待核对”或“已被更新资料替代”。
- 对高风险信息分层处理：私人资料可以帮用户定位、归纳和调用；默认不把密码、账号、证件号、银行卡号、token、备用码等明文扩散到 wiki、稿件或公开内容。
- 用户明确要求在本地个人场景查看某条私人资料时，可以协助定位；除非用户明确要求，不在最终回复中粘贴完整秘密值。
- 大文件、长书、长 PDF 分章处理，避免一次吞完导致噪音和遗漏。
- 热路径知识放进结构化 wiki；冷资料留在归档或 raw，需要时再检索。
- 所有重要整理都要可回溯到原始来源。
- AI 可以辅助整理和执行，但涉及系统设置、账号、密钥、财务、医疗、法律、删除文件等高风险动作时，必须先说明风险并等待明确授权。

## 连接各 AI

- 资料库根目录的 `AGENTS.md` 是所有 AI 的入口，指向本规则。
- `CLAUDE.md` 给 Claude 使用，内容应与 `AGENTS.md` 保持一致或指向同一套规则。
- ChatGPT、Codex、Claude、Obsidian 插件等都应先读 `LLM知识库系统/index.md` 和本文件，再开始整理或写稿。
- AI 输出的长期结论必须回写到 `wiki/`、`知识管理/`、`queries/` 或稿件项目，不只留在聊天窗口。
- 不同 AI 改同一批笔记时，以 `log.md` 记录动作，避免重复整理或互相覆盖。

## 命名和链接

- 页面名优先使用中文自然标题，不强行英文。
- 同一主题只保留一个主页面；别名、旧标题、近义词放在页面开头。
- 链接使用 Obsidian 双链，例如“双中括号 + 页面名”，避免在规则说明里制造无意义空链。
- 标签只做粗分类，主要依靠双链和索引建立关系。

## 维护节奏

- 每日：快速记录灵感，不强迫整理。
- 每周：整理灵感库，把可写选题推进到稿件项目。
- 每周：整理知识管理的新资料和散落操作笔记。
- 每月：做一次 wiki lint，合并重复主题，更新索引，检查过期知识。
- 每次成稿后：回链来源，更新稿件状态，沉淀可复用方法。
